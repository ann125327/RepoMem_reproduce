## 背景与解决的问题

### 研究背景
随着大语言模型（LLM）在软件工程任务中的应用日益广泛，代码定位（Code Localization）成为仓库级软件工程任务（如缺陷修复）中的关键前提步骤。代码定位指的是在大型代码库中**精确定位需要修改的文件和代码段**以解决特定问题。

现有方法主要分为三类：
1. **基于检索的方法**：使用词法或语义匹配对代码片段进行排名
2. **智能体方法**：为LLM配备工具集与环境交互来收集信息
3. **过程化方法**：使用预设计的流程直接调用LLM进行定位

当前最先进的定位框架**LocAgent**（Chen et al., 2025b）将代码库解析为有向异构图，捕捉代码结构和依赖关系，使智能体能够更有效地导航和推理。

### 核心问题
尽管已有进展，当前方法存在一个关键局限：**它们将每个问题都视为全新的谜题，从头开始解决，假设对仓库没有任何先验知识**。这与人类开发者的工作方式形成鲜明对比：

- **人类开发者**会积累并利用长期的仓库记忆：
  - 对核心模块功能的理解缓存
  - 各种重复出现的缺陷模式与其可能的修复位置之间的关联
  - 通过长期接触形成的代码库专业知识

- **现有智能体**：
  - 每次任务都从零开始
  - 不记得之前的修改历史
  - 缺乏对代码库演化的整体理解

论文通过一个具体失败案例说明了这个问题：在Django仓库中，LocAgent成功追踪到一些初始关键实体，但**未能深入推理以精确定位错误源**，导致定位失败。而有经验的开发者可能会利用**情节记忆**（episodic memory，过去关于迁移系统的问题/代码更改）或**语义记忆**（semantic memory，负责处理导入的模块）来指导搜索。

### 问题定义
**如何为代码定位智能体配备类似人类开发者的仓库记忆？** 论文提出利用仓库的**提交历史**作为构建这种记忆的天然记录。

## 创新点

1. **首次将提交历史作为智能体记忆来源**：提出利用仓库的提交历史——一个丰富但未被充分利用的资源——来构建智能体的长期记忆。

2. **双重记忆结构设计**：
   - **情节记忆**：具体过去问题及其解决方案的记忆
   - **语义记忆**：对代码库最活跃部分功能的概括性理解

3. **轻量级、模块化集成**：记忆工具设计为可轻松集成到现有智能体框架中，无需大规模架构更改。

4. **基于实证的洞察**：发现提交频率高的文件（"热点"）与缺陷可能性强相关，这与缺陷预测领域的研究一致。

5. **检索方法创新**：发现稀疏检索方法（BM25）在代码相关检索中优于稠密检索，因为代码实体的"刚性词汇"特性。

## 主要方法

论文设计了两种简单的记忆机制来增强现有框架：

### 3.1 过去提交的情节记忆

**记忆构建**：
- 从仓库最近的提交历史构建结构化语料库
- 存储代码补丁及其丰富元数据：提交消息、时间戳、关联的问题链接
- 仅包含待解决问题之前的提交（避免污染）
- 过滤掉与测试实例文本重叠的问题和相关提交（防止泄露）

**记忆接口**：
1. **SearchCommit(query, top_k)**：
   - 执行基于案例的检索
   - 使用BM25匹配查询与提交消息
   - 返回前k个相关提交的排名列表（包括唯一ID、消息、修改文件）

2. **ExamineCommit(id)**：
   - 根据ID检索提交的完整上下文
   - 包括完整的代码补丁（diff格式）和任何链接的问题

### 3.2 活跃代码功能的语义记忆

**理论基础**：**频繁修改的文件是"开发热点"**——要么是仓库功能的核心区域，要么正在经历活跃变更。缺陷预测研究早已确认，高代码变动率和频繁修改与缺陷倾向性强相关。

**记忆构建**：
1. **识别热点文件**：分析提交历史，识别前k个最常编辑的文件（k远小于仓库文件总数）
2. **生成功能摘要**：对每个热点文件，使用LLM读取源代码并提炼其功能为高级自然语言摘要
3. **创建语义知识库**：映射关键文件到其核心职责，专注于仓库最动态的部分

**记忆接口**：
1. **ViewSummary(file_name)**：检索特定文件的缓存摘要
2. **SearchSummary(query, top_k)**：在整个文件摘要集合上执行基于关键词的搜索

### 数学公式解释

论文中主要涉及检索算法BM25，其核心公式为：

```
score(D, Q) = Σ_i IDF(q_i) · (f(q_i, D) · (k1 + 1)) / (f(q_i, D) + k1 · (1 - b + b · |D| / avgdl))
```

其中：
- `D`：文档（这里是提交消息）
- `Q`：查询
- `q_i`：查询中的第i个词语
- `IDF(q_i)`：词语q_i的逆文档频率
- `f(q_i, D)`：词语q_i在文档D中的频率
- `|D|`：文档长度
- `avgdl`：平均文档长度
- `k1, b`：可调参数（通常k1∈[1.2,2.0], b=0.75）

论文发现，使用**LLM基础的分词器**（能够识别代码实体名称）优于标准空格分词器。这是因为代码相关话语有独特的词汇，如`MigrationWriter`和`OperationWriter`在语义上接近但功能上非常不同。稀疏检索方法依赖于精确关键词匹配，擅长处理这种"刚性词汇"。

### 与LocAgent的集成

记忆工具设计为模块化，可直接集成到现有智能体框架中。论文将其集成到**LocAgent**——一个基于ReAct范式的最先进定位框架中。

**LocAgent核心工具**：
- `SearchEntity`：在代码库中搜索匹配关键词查询的实体
- `TraverseGraph`：从起始实体执行多跳、类型感知的广度优先搜索来探索代码关系
- `RetrieveEntity`：获取特定代码实体的完整源代码和详细信息

**集成方式**：简单地将基于记忆的工具扩展到动作空间中。

**协同效应**：
- 智能体可以使用记忆搜索工具获取相关提交或文件
- 结合具体检查形成基于经验的假设
- 然后使用LocAgent的工具对这些候选实体周围的代码实体进行更详细的调查

这种集成创建了**高级记忆引导方向**与**低级结构代码分析**之间的强大协同作用。

## 技术栈与技术实现

### 技术栈
1. **大语言模型**：GPT-4o (2024-05-13) 作为骨干LLM
2. **检索系统**：BM25稀疏检索，使用LLM基础的分词器
3. **图数据库**：LocAgent的代码图表示
4. **数据处理**：提交历史爬取和预处理管道
5. **基准测试**：SWE-bench-verified 和 SWE-bench-live

### 实现细节

#### 记忆构建参数
- **提交窗口**：考虑给定问题基本提交前的7,000次提交
- **语义记忆大小**：识别前200个最常编辑的文件用于构建语义记忆
- **摘要生成**：使用LocAgent框架+GPT-4o生成文件功能摘要，每个文件平均成本$0.23
- **情节记忆链接**：依赖提交与问题之间的显式链接（如提交消息中的"Fixes #123"）

#### 离线构建开销
- 在SymPy仓库（SWE-bench-Verified中历史最大的仓库，包含60k+历史提交）上测量
- 完整记忆构建约45分钟：
  - 约37分钟用于数据爬取（提交、问题等）
  - 约8分钟用于并行预处理和语义记忆生成
- **一次性设置成本**：每个仓库只需构建一次

#### 在线延迟
- 在SWE-bench-Verified的50个示例随机子集上分析
- 每个实例平均总运行时间：28.6秒
- 内存搜索工具引入的平均开销：仅0.22秒/实例
- LocAgent标准工具成本：0.37秒/实例
- **主要延迟来自LLM推理**：确认集成仓库内存对智能体循环增加最小延迟

#### 令牌长度分析
- **LocAgent工具**：
  - RetrieveEntity：7.10K令牌
  - TraverseGraph：2.98K令牌
  - SearchEntity：1.66K令牌
- **记忆工具**：
  - SearchCommit：2.11K令牌
  - ExamineCommit：1.81K令牌
  - ViewSummary：1.67K令牌
  - SearchSummary：6.18K令牌

## 实验效果

### 实验设置

#### 数据集
1. **SWE-bench-verified**：包含来自12个仓库的500个示例
2. **SWE-bench-live**：使用其`lite`和`verified`分割的交集创建的高质量子集，过滤需要修改五个或更少文件的实例，得到来自62个仓库的130个示例

#### 基线方法
1. **CodeRankEmbed**：领先的基于检索的方法，使用大规模训练和负例挖掘
2. **Agentless**：领先的过程化方法，向LLM提示仓库结构
3. **LocAgent**：最先进的智能体定位框架，RepoMem方法直接构建于此

#### 评估指标
文件级定位性能通过**Accuracy@k**评估（遵循先前工作），定义为预测的前k个文件完全覆盖真实文件的示例百分比。

### 主要结果

#### 整体性能（表1）
| 方法 | SWE-bench-verified | SWE-bench-live |
|------|-------------------|----------------|
| | Acc@1 | Acc@3 | Acc@5 | Acc@1 | Acc@3 | Acc@5 |
| CodeRankEmbed | 29.6 | 45.1 | 54.3 | 26.2 | 44.6 | 52.3 |
| Agentless | 53.3 | 67.8 | 71.4 | 40.0 | 60.0 | 62.3 |
| LocAgent | 64.8 | 70.4 | 71.6 | 59.2 | 60.8 | 63.1 |
| RepoMem（仅情节） | 67.8 | 72.4 | 74.3 | 60.0 | 61.5 | 64.6 |
| RepoMem（仅语义） | 65.0 | 71.0 | 72.8 | 56.9 | 61.5 | 63.9 |
| **RepoMem（完整）** | **68.6** | **74.5** | **76.5** | **60.8** | **63.9** | **66.2** |

**关键发现**：
- RepoMem在两个基准测试上一致优于所有基线
- 在SWE-bench-verified上，RepoMem达到76.5% Acc@5，比强大的LocAgent基线绝对提升4.9%
- 仅使用情节记忆或仅使用语义记忆都能显著提升LocAgent性能
- 两种记忆组件结合时效果最佳，表明它们提供互补信息

- **历史有限的仓库性能下降**：因为记忆包含太少相关信息，智能体探索这个稀疏历史可能分散注意力而非有帮助

### 深入分析

#### 智能体行为转变（图3）
引入记忆显著改变了智能体的问题解决策略：
- **减少对穷举探索工具的依赖**：TraverseGraph使用大幅减少
- **减少直接代码检查**：RetrieveEntity使用减少
- **反映了从暴力导航到更有针对性、假设驱动调查的战略转变**

这种转变更接近有经验人类开发者的工作流程。

#### 效率分析（表3，图4）
集成记忆引入了**战略成本效益权衡**而非统一开销：

**成本分布**：
- 额外支出主要分配给解决困难问题——最大的成本增加发生在LocAgent失败的示例中
- 这表明方法战略性地投资额外资源解决基线无法解决的挑战性问题

**高度可变的成本影响**：
- 对于许多问题，RepoMem比LocAgent便宜得多（记忆提供了更直接的解决提示）
- 对于一些其他问题，RepoMem更昂贵（记忆无果，只增加了开销和分散注意力）
- 这种异质性突显了平均成本可能是误导性指标

**战略使用记忆的未来方向**：训练智能体更战略性地决定何时使用记忆工具。智能体可以先评估问题的新颖性，学会对与过去经验相关的问题依赖记忆，而对前所未有的问题默认使用第一原则探索。

#### 检索方法比较（表4）
在Django仓库上比较三种检索方法：

| 检索方法 | django/django Acc@1 | Acc@3 | Acc@5 |
|----------|---------------------|-------|-------|
| 稠密检索 | 65.8 | 71.9 | 73.6 |
| BM25（空格分词） | 67.1 | 74.5 | 77.9 |
| **BM25（LLM分词）** | **70.1** | **76.6** | **79.7** |

**发现**：
- 稀疏检索方法显著优于稠密检索
- 使用LLM基础分词器（识别代码实体名称）优于标准空格分词
- 假设：代码相关话语有独特词汇，如`MigrationWriter`和`OperationWriter`在语义上接近但功能上不同。稀疏检索方法擅长处理这种"刚性词汇"

#### 错误分析
主要失败模式发生在**记忆检索产生关于问题的有用信息很少时**，源于问题的新颖性或检索方法的不足。

在这种情况下：
- 智能体接收无关信息，可能污染其推理上下文并分散注意力
- 可能导致性能比基线更差（如表2中历史稀疏的仓库所示）

#### 下游影响（表7）
改进的定位准确性直接转化为更高的解决率：

| 方法 | Loc Acc@5 | Resolve Rate |
|------|-----------|--------------|
| CodeRankEmbed | 54.3 | 26.8 |
| Agentless | 71.4 | 36.2 |
| LocAgent | 71.6 | 37.0 |
| RepoMem（仅情节） | 74.3 | 38.8 |
| RepoMem（仅语义） | 72.8 | 37.6 |
| RepoMem（完整） | **76.5** | **40.4** |

**确认**：定位性能与最终解决率强相关，这与先前发现一致。

## 缺点与展望

### 当前方法的局限性

1. **提交-问题链接质量依赖**：情节记忆构建依赖提交与问题之间的显式链接（如"Fixes #123"）。这些链接可能嘈杂或缺失，降低了记忆检索的召回率。

2. **稀疏历史仓库的负面影响**：对于提交历史有限的仓库，记忆可能包含太少相关信息，智能体的探索可能分散注意力而非有帮助，导致性能下降（表2中"其他"类别下降13.1%）。

3. **检索噪声可能导致性能下降**：当记忆检索产生无关信息时，可能污染LLM推理上下文并分散注意力，这是一个LLM的已知挑战。

4. **固定窗口大小**：使用固定提交窗口（7,000次提交）作为直接启发式方法，可能不是最优的。

### 未来工作展望

1. **更复杂的记忆过滤策略**：借鉴JIT-SDP研究中的时间衰减、开发者经验过滤或共变更历史等策略，优化记忆效率和相关性。

2. **适应性记忆使用**：训练智能体更战略性地决定何时使用记忆工具。智能体可以先评估问题的新颖性，对与过去经验相关的问题依赖记忆，对前所未有的问题使用第一原则探索。

3. **改进的提交-问题链接**：采用更健壮的链接策略来缓解显式链接嘈杂或缺失的问题。

4. **个性化记忆构建**：考虑开发者特定的提交模式或专业知识领域，构建更个性化的记忆。

5. **扩展到其他软件工程任务**：将仓库记忆方法扩展到代码定位之外的其他任务，如代码补全、重构或文档生成。

6. **动态记忆更新**：随着代码库演化，设计机制动态更新记忆而非完全重新构建。

7. **跨仓库记忆**：探索在不同但相关的仓库之间共享记忆的可能性。

## 专有名词解释

1. **Code Localization（代码定位）**：在仓库级软件工程任务中识别需要修改的特定文件和代码段的过程。

2. **Repository Memory（仓库记忆）**：智能体对代码库的长期知识积累，包括过去更改的记忆和代码功能的抽象理解。

3. **Episodic Memory（情节记忆）**：具体过去事件（如提交、问题解决）的记忆，提供基于案例的知识。

4. **Semantic Memory（语义记忆）**：对代码库功能和架构的概括性理解，提供高层次背景知识。

5. **LocAgent**：最先进的代码定位智能体框架，将代码库解析为异构图以支持智能体导航。

6. **ReAct Paradigm**：Reasoning + Acting范式，智能体迭代循环通过"思考、行动、观察"步骤与环境交互。

7. **BM25**：经典的信息检索算法，基于词频和逆文档频率对文档进行排名，特别适合关键词丰富、半结构化的文本。

8. **SWE-bench**：软件工程基准测试，评估LLM解决真实GitHub问题的能力。

9. **JIT-SDP（Just-in-Time Software Defect Prediction）**：及时软件缺陷预测，旨在特定代码更改（如提交）后立即预测其有缺陷的可能性。

10. **Development Hotspots（开发热点）**：频繁修改的代码区域，通常与高缺陷倾向性相关。

复现 baseline 与初步实验

接下来是我的初步实验计划。

我准备以 RepoMem 作为 baseline。原因是它的任务、数据集、指标和 ablation 都比较明确，比较适合先做轻量复现。

第一步，我会选择 SWE-bench-verified 的一个子集，或者选择一两个 commit history 比较丰富的仓库。然后构建 commit memory，包括 commit message、diff、modified files 和 linked issue。

第二步，先实现一个轻量版 SearchCommit，比如用 BM25 检索历史 commit，复现文件级 localization Acc@k。这个阶段主要验证 repository memory 是否能在我的设置里带来稳定收益。

第三步，在 RepoMem 检索之后加入 validity 判断。比如给每条 memory 加上 source commit、affected files、valid range 和 status，然后检查当前版本是否发生了 API change、module refactor、dependency upgrade 或 test semantics change。

最后做对比实验：普通 RepoMem 检索和加入 hygiene filtering 或 reranking 之后，是否能降低 stale memory 的召回，提高 localization accuracy，或者进一步提高 patch resolved rate，同时观察 token cost 是否可控。

评价指标上，我会先看 Localization Acc@k、Retrieval Precision@K、stale memory rate、valid memory rate 和 token cost。如果前面的定位实验稳定，再进一步看 patch resolved rate。

这个实验部分的落点是：我的方向不是再做一个普通的 memory retrieval，而是在 RepoMem 的 relevance 之上，进一步研究 repository-evolution-driven validity。也就是让代码库记忆能够随着代码库演化被持续维护、净化和版本化。
